# 04 · 记忆与上下文

> 2026 年面试的重灾区。**上下文不是容器，是有预算、有生命周期的资源。**
> 这一章要能把「长对话越来越慢、越来越乱」拆成可定位、可度量的工程问题。

---

## 1. 先建立心智模型：Messages List 才是真实记忆

模型本身**无状态**。每一次请求，都是把完整 `messages` 列表重新发一遍。
所谓「记忆」，本质是**应用每一轮决定往这个列表里放什么**。

```
系统提示 + 工具定义 + 检索片段 + 历史消息摘要 + 最近 N 轮 + 本轮输入
                         ↓
                   上下文窗口（有限预算）
```

因此上下文工程回答的问题不是「怎么写好一句提示词」，而是：
**这一轮，哪些 token 值得占用窗口？被挤出去的信息放到哪、什么时候取回来？**

### 为什么上下文变长会变差

- **context rot**：无关内容稀释注意力，指令遵循度下降。
- **lost-in-the-middle**：放在中间位置的信息容易被忽略，首尾效果更好。
- **位置敏感**：系统指令、关键约束应放在结构上的显著位置并适当重复。
- **成本与延迟**：注意力 O(n²)、KV Cache 线性增长、每轮重发历史。

## 2. 记忆分层（面试标准答案要分层讲，不要只说「向量库」）

| 层 | 对应实现 | 存什么 | 取回方式 | 生命周期 |
|---|---|---|---|---|
| **工作 / 短期记忆** | `messages` 列表 | 当前任务的输入、工具调用与观察 | 每轮直接携带 | 会话内 |
| **情景记忆** | 会话记录、事件表（带时间戳） | 「上周三用户改了交付日期」这类事件 | SQL / 时间范围查询 | 跨会话、长期 |
| **语义记忆** | 向量库 / 知识库 / 用户画像 | 长期事实与领域知识 | 向量检索 + RAG | 长期、可更新 |
| **程序性记忆** | Skills（`SKILL.md`）、SOP | 流程、操作指南、检查清单 | 按需加载 / 渐进式披露 | 版本化管理 |

补充两个常被追问的点：

- **长期记忆 ≠ RAG**：RAG 检索的是外部知识库（通常人人可用、与用户无关）；记忆存的是与「这个用户 / 这个 Agent」相关的状态与经历，涉及权限、时效、冲突与删除。
- **记忆要有写入策略**：不是什么都存。判断标准通常是「未来是否会改变决策」+「是否可验证」+「是否允许保存（隐私）」。

## 3. 上下文工程的四种手段（Anthropic）

| 手段 | 做法 | 适用 | 风险 |
|---|---|---|---|
| **Compaction 压缩** | 临近窗口阈值时，把旧历史总结成结构化摘要 | 长对话、长任务 | 丢关键细节；压缩本身要花一次模型调用 |
| **Structured note-taking** | Agent 主动把进度、待办、关键结论写到外部文件/DB | 跨多个上下文窗口的长任务 | 笔记写错会持续误导；需校验 |
| **Sub-agent 隔离** | 子任务交给独立上下文的子 Agent，只回传摘要 | 调研、多源并行 | token 成本上升（约 15× 于普通聊天量级） |
| **Just-in-time retrieval** | 上下文只放标识符 / 路径，用到时再加载数据 | 大文件、大工具结果 | 多一次 IO，需缓存 |

### 压缩放在链路哪一步？

**先裁剪/压缩，再向量化入库**。原因：把一堆原始工具输出直接塞进向量库，会产生大量近重复碎片，检索噪声大、召回互相污染。

推荐顺序：

```
1. 规则层：去重、丢弃已消费的工具输出、只保留最近 N 轮原文
2. 卸载层：大结果写入外部存储，上下文里只留引用 ID
3. 摘要层：对剩余历史做结构化压缩（保留：目标、约束、已确认事实、待办、失败记录）
4. 校验层：把「不可丢清单」逐项比对，缺了就补回
5. 入库层：只把有长期价值的结构化内容写入长期记忆 / 向量库
```

**避免一次性大段压缩打断体验**：设阈值提前渐进压缩（如到 70% 就开始分批），异步执行、保留最近若干轮原文、把压缩动作做成可回滚的 checkpoint。

### 工具结果怎么压缩

- **原地压缩**（同一模型、同一链路）：快、便宜，但会占用主链路注意力，压缩质量受已有上下文污染。
- **交给独立模型 / 子 Agent**：隔离得干净、质量稳定，但多一次调用、增加延迟。
- 经验：结果超过某个 token 阈值才压；结构化结果（表格、JSON）用代码裁剪，别交给模型。

## 4. 长任务的两个老大难

### 目标迷失

多轮之后模型开始围着局部细节打转，忘了原始目标。工程解法：

- 把**目标、约束、完成标准**固定在 system / 每轮开头的显著位置（状态卡）。
- 每轮输出前先复述当前子目标与进度。
- 用外部 checklist 驱动，而不是靠模型自己记得。

### 「无限记忆」的悖论

模型窗口有限 → 必须丢弃信息；但丢弃就可能丢关键事实。
正确答案不是「找个无限窗口」，而是**分层 + 可检索 + 可校验**：窗口里只留当前决策所需，其余进可寻址的外部存储，用检索按需取回，并对压缩结果做保真校验。

## 5. 记忆系统的工程细节（追问区）

| 问题 | 要点 |
|---|---|
| 存什么 / 何时写 | 任务结束或关键事实确认时写；异步抽取 + 去重 + 置信度；不存中间噪声 |
| 怎么召回 | 混合检索（时间 + 语义 + 实体），带相关性阈值与时效衰减 |
| 防止相互污染 | 按会话 / 用户 / 任务命名空间隔离；元数据过滤；召回后重排与去重（MMR） |
| 新旧冲突 | 带时间戳与来源，以新覆旧或标记待确认；保留版本历史 |
| 用户要求删除 | 记忆必须可寻址、可级联删除（向量库 + 关系库 + 摘要缓存 + 派生笔记） |
| 选型 | 会话/事件用关系库或 KV；语义检索用向量库；高频小状态用 Redis；别全塞一个库 |
| 量化评估 | 记忆命中率、召回噪声率、对任务成功率的贡献（做消融：去掉记忆层再测） |
| 权限与隐私 | 按用户隔离、加密、最小化保存、审计；跨 Agent 共享要有明确授权 |

### 上下文污染 vs 工具污染

- **上下文污染**：历史里混入了错误/过期/无关内容，模型持续被带偏 → 压缩、隔离、开新 session。
- **工具污染**：工具描述太多、返回太长或含恶意指令，挤占并干扰窗口 → 裁剪工具集、卸载结果、把返回当不可信数据。

判断要不要「新开 session」：如果错误已经写进多轮历史、且模型反复引用它，压缩往往救不回来，带干净状态卡重开更省。

## 6. 易错点与面试陷阱

| 常见错答 | 更准确的回答 |
|---|---|
| 「短期记忆=窗口，长期记忆=向量库」 | 太粗；要分工作/情景/语义/程序性四层，并讲写入策略与权限 |
| 「上下文不够就换长上下文模型」 | 只解决容量，不解决注意力稀释、成本与延迟 |
| 「压缩交给模型总结一下就行」 | 要讲顺序、不可丢清单、保真校验、渐进压缩与回滚 |
| 「长期记忆就是 RAG」 | RAG 是外部知识检索；记忆带用户状态、时效、冲突与删除语义 |
| 「上下文越长效果越差只因为贵」 | 还有 context rot 与 lost-in-the-middle，是质量问题不是成本问题 |
| 「摘要存起来就完事」 | 摘要会失真并持续误导；要保留原文引用、版本与可回溯 |

## 8. 高频面试题（附答题要点）

1. **短期记忆和长期记忆怎么实现、怎么区分？**
   → 短期是 messages 列表（会话内、每轮重发），长期是外部可寻址存储（跨会话、需检索）；中间还有情景与程序性层。
2. **长期记忆和 RAG 有什么区别？**
   → 前者是与主体相关的状态与经历，涉及写入、时效、冲突、删除与权限；后者是外部知识检索。
3. **记忆模块选什么数据库，依据是什么？**
   → 按访问模式分：事件/时间用关系库，语义用向量库，热状态用 KV；看一致性、可删除性、查询模式。
4. **记忆如何召回？怎么避免不同问题召回的记忆互相污染？**
   → 混合检索 + 阈值 + 时效衰减 + 命名空间/元数据隔离 + 去重重排。
5. **在 Agent 项目中怎么设计上下文管理机制？**
   → 预算制：固定状态卡 + 最近原文 + 摘要 + 按需检索；设阈值渐进处理，全程可追踪。
6. **上下文压缩放在链路哪一步？先压缩再向量化还是反过来？**
   → 先规则裁剪/卸载/压缩，再入库，避免近重复碎片污染检索。
7. **长对话怎么处理？滑动窗口 + 摘要具体怎么落地？**
   → 保留最近 N 轮原文 + 结构化摘要 + 不可丢清单；阈值触发、异步、可回滚。
8. **快到窗口阈值时，怎么避免一次性大段压缩打断用户体验？**
   → 提前到 70% 分批、异步、保留热区原文、增量更新摘要。
9. **工具调用结果怎么压缩？原地还是交给另一个模型？**
   → 结构化结果用代码裁；非结构化按阈值决定；独立模型质量更稳但多一次延迟，讲清权衡。
10. **除了压缩，还有哪些规避窗口限制的方案？**
    → 卸载到外部存储只留引用、子 Agent 隔离、just-in-time 检索、按角色裁剪工具、结构化状态卡。
11. **多轮长任务怎么避免「目标迷失」？**
    → 目标与完成标准常驻显著位置、外部 checklist 驱动、每轮复述子目标。
12. **怎么区分上下文污染和工具污染？什么时候该新开 session？**
    → 看污染源是历史还是工具描述/返回；错误已被多轮引用且反复复现时，带状态卡重开。
13. **如何保证压缩不丢关键内容？失真怎么缓解？**
    → 不可丢清单逐项校验、保留原文引用、压缩前后做一致性检查、失败可回滚。
14. **长期运行 Agent 面对数月历史，记忆怎么持续优化？**
    → 分层归档、时效衰减、命中反馈淘汰、定期重摘要、冲突消解与版本化。
15. **记忆有没有量化指标？怎么评测贡献？**
    → 命中率、噪声率、任务成功率，做去掉记忆层的消融对比。
16. **用户要求删除记忆，系统要怎么支持？**
    → 可寻址 ID + 级联删除所有派生（向量、摘要、缓存、笔记）+ 审计留痕。

## 9. 本章必须记住的三句话

1. **模型无状态，messages 列表才是真实记忆；上下文工程就是决定每轮放什么。**
2. **压缩的顺序是「裁剪 → 卸载 → 摘要 → 校验 → 入库」，且必须有不可丢清单。**
3. **记忆不是「存得多」，是「取回得准、能改、能删、有权限」。**
